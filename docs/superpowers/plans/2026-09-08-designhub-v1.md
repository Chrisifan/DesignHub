# DesignHub V1 Implementation Plan

> **Superseded by the [2026-10-14 V1 completion plan](2026-10-14-designhub-v1-completion.md).** 本文包含已移除的多文档、修订、品牌包与 Workbench 范围，仅保留历史记录。

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 实现已确认的完整桌面首版，使用户从创建设计师与项目走到可编辑物料、工具修改、版本署名、离线管理与可追溯交付。

**Architecture:** 单应用、八个业务模块，先验证桌面与存储契约，再按可运行能力推进。项目级元数据与不可变资源/版本构成数据基础，画布和对话调用同一用例。依赖供应商由固定适配器隔离，不建立任意插件框架。

**Tech Stack:** TypeScript / React renderer；Electron desktop runtime（已按用户决定选定）；SQLite、画布、测试和图像库均经研究门槛决定具体版本。

**Spec:** [首版架构与功能基线](../specs/2026-09-08-designhub-v1-design.md)，[UI 应用说明书](../../product/APPLICATION-GUIDE-FOR-UI.md)，[UI 基础规范](../../product/UI-FOUNDATIONS.md)。

**Status:** 2026-09-09 经用户确认，Q1–Q66 已冻结为 V1 实施基线。后续依赖研究和工程实验按门槛推进；新增或修改产品能力先登记基线变更、影响模块与回归范围。

## Global Constraints

- 首版正式支持 macOS 与 Windows；Linux、完整移动编辑器和多人并发写入不在首版。
- 用户数据本地保存；工作区自包含；项目独立保存元数据，项目包携带所需依赖。
- 先调研成熟框架或第三方库，再写对应功能实现；未核验候选不等于选型。
- 按模块先写测试用例和 checklist，再实现并对照验证；改到已验证模块必须记录影响并回归。
- 严格按照功能计划，不增加预期之外的插件系统、微服务、事件总线、同步协议或泛化工作流引擎。
- 所有自写函数遵守用户“箭头函数”要求；不能默许原生代码例外。
- 核心浏览、编辑、历史、检索、导出、备份离线可用；云请求不在重连后静默提交。
- 无平台账户；提供方密钥只存系统安全存储，不进项目、包、备份、日志。
- 对话、图像生成与编辑能力可分别配置；不自动切换模型或提供方。
- 首版简体中文与英文；非画布流程键盘、焦点和读屏可用。
- UI 只使用基础规范列入 allowlist 的 DesignHub Figma Frame；明暗主题共用布局，窗口、四字按钮、防换行、抽屉、动效和降级规则对所有模块生效。
- M01 可先依据已确认的 UI 基础规范实现窗口外壳；其余模块开始视觉实现前，须取得 UI 设计师对相关页面、适用状态、双语和响应式行为的交付或明确确认。领域逻辑和技术验证可先行。
- 首版只提供可预览、由用户主动导出的本地诊断包，不实现自动网络发送或诊断接收端。

## 0. 如何执行

本任务交付规划与选型记录。目前没有正式应用工程、包管理脚本或 Git 仓库；历史 Tauri/SQLite 探针不属于 Electron 工程。文中代码是未来目标文件的契约/测试片段，不表示这些文件已存在或测试已运行。

用户已确认 Electron 基线，网络资料核验部分完成；运行时样例和真实供应商调用仍按模块验证。先读 [依赖研究门槛](../../research/DEPENDENCY-GATES.md)。默认使用本会话内逐任务执行，若用户选择子代理流程再使用对应技能，不在规划阶段派发实现。

每个子计划含明确目标文件、输入输出契约、首个可执行回归测试、实现行为、补充用例和 checklist。选型涉及的安装命令、准确依赖版本在研究通过后写入模块记录和 lockfile；不提前虚构版本。模块测试中的源码导入在实现前应失败，随后才写最小实现。

### 通用交付循环

1. 读对应子计划、功能章节、适用的 UI 基础规范和上游公开接口；检查当前工作树，保留用户修改。涉及视觉实现时，先核对该模块 UI 设计交付或明确确认；M01 窗口外壳可直接使用已确认基础规范。
2. 完成模块对应 G 门槛，记录官方来源及实验证据。
3. 创建 `docs/verification/Mxx.md`：填写模块测试用例（前置、操作、预期）、任务 checklist、触及文件及受影响模块。此步先于实现。
4. 写一个行为失败测试，运行并记录失败原因；环境/安装错误不能当成行为 Red。
5. 实现使测试通过的最小用例，继续按场景扩展；UI、存储和原生桥接各只维护自己的职责。
6. 运行该模块测试、类型/编码检查与适用集成/手验；逐项填写证据，未验证不打勾。
7. 如修改已验证模块，把其状态改为需回归，记录原因并跑受影响用例；跨文件共享契约变动测试所有直接消费者。
8. 更新登记、review diff；实现阶段若已有 Git 仓库，按明确文件暂存并提交单个可验收任务。当前文档阶段不初始化 Git。

## 1. 文件与验证命令约定

工程结构按架构说明。M01 建立以下命令契约，后续不能只写“跑测试”而没有入口：

| 目标命令 | 意义 | 何时可运行 |
| --- | --- | --- |
| `pnpm lint` | 代码组织规则和箭头函数检查 | M01 工程建立后 |
| `pnpm typecheck` | 应用与测试 TS 类型检查 | M01 后 |
| `pnpm test:unit -- <path>` | 指定行为测试，不默认跑所有模型请求 | M01 后 |
| `pnpm test:integration -- <path>` | 临时目录、真实数据存储与恢复 | M02 建立入口后 |
| `pnpm test:e2e -- <path>` | 浏览器或可测 UI 层交互，假网络显式标识 | M01 UI harness 后 |
| `pnpm test:native` | 选定宿主的真实桌面冒烟 | G01 R06 通过后，分别记录 OS |
| `pnpm build` | 类型与打包构建 | M01 后 |

pnpm 是计划的脚本约定候选；若现有工程后来采用其他管理器，机械统一这些命令并记录，不并存两套 lockfile。付费提供方验收单独显式运行，不作为普通测试自动联网。

## 4. 首版交付闸门

- [ ] P01–P20 对应流程完成，UI 说明书的贯穿案例及六个异常案例均有证据。
- [ ] M01–M08 所有功能验证通过；没有以测试替身冒充真实工具能力。
- [ ] macOS 与 Windows 真机完成创建、保存、重启恢复、编辑、生成、导出与包导入。
- [ ] 所有已记录依赖通过研究，精确锁版本、许可证与打包归属明确。
- [ ] 核心离线流程可用，联网恢复不自动提交云任务；缺 Key/缺字体/缺外接盘可恢复。
- [ ] 历史与署名不可被默认设计师变更、档案更新或删除影响。
- [ ] 项目包/备份中无密钥，交付包无内部聊天和不必要源资料。
- [ ] 本地诊断包经用户预览并主动导出，不包含素材、项目结构、路径、提示词、创作内容或密钥；应用没有自动诊断上传。
- [ ] 每次改动影响的已验证模块已重新验证，无未关闭的需回归状态。
- [ ] 双语与可访问性检查、性能基准、系统安装签名/公证/更新链路有真实记录。
