# Designer Persona UI Design

Date: 2026-09-11. Status: approved in conversation; pending written-spec review.

## Goal

Reimplement the example workspace's design display and new-design surfaces around an AI designer persona. The persona is a generated creative identity, not a real person or legal author. It makes the selected designer immediately recognizable while preserving the design material as the primary object of evaluation.

## Scope

- Update the example design gallery and project detail presentation (P02/P05) so every design shows its contributing designer through an avatar, name, and immutable profile version.
- Replace the current compact new-project modal with a P03/P04 creation surface where the active designer's persona is the principal supporting visual.
- Rework the P10/P12 designer library and detail view around persona cards.
- Add a P11 create-designer flow with description and portfolio-analysis entry points, three selectable persona candidates, review, and explicit publish intent.
- Keep all new behavior session-only. It must be labeled as example UI until M03 profile persistence and M06 model execution are connected.

## Explicit Non-Goals

- No real model invocation, key handling, portfolio upload, web scraping, image generation, or profile persistence in this UI round.
- No changes to M02 storage, provider connection, workspace creation, revision attribution, or Electron native-window contracts.
- No claims that example persona artwork was generated by a live model.

## Visual Direction

The selected direction is **character hero**. The new-design screen uses a full-height, generated persona image as the companion visual for the current designer. The design cover remains the primary visual on gallery and project pages; those contexts use a compact avatar and attribution strip instead of a large persona image.

Persona artwork is stylized character portraiture, comparable to an MBTI character system rather than a photorealistic person. A selected source image supports avatar, half-body, and full-body crops. The crop container has a fixed aspect ratio so names, translated text, and image loading cannot reflow cards.

Existing dark/light semantic tokens remain the only color source. Primary represents selection, secondary represents AI and candidate generation, tertiary represents ready/published, and error represents failure. The character image itself is not recolored by theme.

## Page Behavior

### Design Display: P02/P05

- Project cards remain image-first. A compact attribution rail overlays the lower edge with the designer avatar, profile name, and version.
- Project detail includes an active-designer strip above the document list. It shows a half-body persona, a one-sentence creative tendency, and a compact designer switcher Popover.
- Clicking an attribution or persona opens the designer detail destination. The current designer is distinct from historical contributors; the UI copy must never imply that a displayed current designer signed every existing work.

### New Design: P03/P04

- Manual brief and conversation brief remain two modes of the same creation draft.
- The left content column contains title, brief, size, selected designer, reference summary, and the primary creation action.
- The right hero column contains the active persona, profile/version, a short working principle, and the selected creation mode. It updates when the designer changes.
- The character supports orientation but never blocks manual creation. A user can create a blank local project without a model connection.
- At 1024--1279px, the hero becomes a collapsible top or side panel; it never compresses required form controls to multi-line buttons. At 1280px and above, it stays visible beside the brief.

### Designer Library and Detail: P10/P12

- The library presents stable persona cards with full portrait, name, style tags, version, status, and signature.
- Detail retains profile rules, version, signature, references, default scope, and projects using the profile. Persona art supports a larger inspection view.
- Cards use text, an icon, and a border for selected/published/default states. They do not communicate state through color alone.

### Create Designer: P11

- The creation form exposes two equal entry modes: description and portfolio analysis.
- Description accepts style, temperament, clothing/shape language, palette, and exclusions. Portfolio mode shows local images/links and requires an explicit rights confirmation before analysis can be requested.
- The actual analysis/generation contract belongs to M06. This UI round presents a clearly labeled example candidate state and cannot announce a real remote result.
- Candidate review renders exactly three fixed-ratio persona cards. Each candidate supports preview and select. Selection is visible through a check icon, label, and border.
- After selection, the review pane previews the persona in its new-design hero and compact design-attribution usages.
- Choosing a candidate only updates an unpublished draft. A separate publish action is required before a profile is represented as published.

## UI State Model

```ts
type PersonaCandidateStatus = 'idle' | 'generating' | 'ready' | 'failed';

type PersonaCandidate = {
  id: string;
  label: string;
  alt: string;
  source: 'description' | 'portfolio' | 'combined';
  status: PersonaCandidateStatus;
  imageUrl?: string;
};

type PersonaDraft = {
  name: string;
  signature: string;
  styleSummary: string;
  rules: string[];
  candidateIds: [string, string, string];
  selectedCandidateId?: string;
  publishState: 'draft' | 'published';
};
```

The current UI uses an in-memory example adapter. M03 replaces draft/profile data with versioned profile storage. M06 supplies candidate generation and portfolio analysis. A real candidate must preserve source, prompt/analysis summary, selected image asset, and model task reference without exposing connection secrets to the renderer.

## Component Boundaries

- `PersonaArtwork`: fixed-ratio image/crop frame, alt text, loading and unavailable states.
- `PersonaCard`: library and candidate presentation; consumes a persona view model and emits select/inspect events.
- `DesignerHero`: new-design companion visual and active-designer strip.
- `NewDesignPage`: manual/conversation creation draft and active-designer selection.
- `CreateDesignerPage`: description/portfolio modes, candidate review, and preview mapping.
- `DesignerLibrary`: owns local example list selection only; it must not own project creation state.

Existing generic button, icon, dialog, field, localization, and theme primitives are reused. No additional UI or animation package is introduced. All authored functions and components use arrow functions.

## States and Errors

- Generating: show staged progress without inventing percentages.
- Partial candidate failure: retain ready candidates, identify the failed candidate, and offer retry when M06 is connected.
- No model connection: retain user input and explain that a local draft can still be saved; do not show generated artwork.
- Candidate selected but unpublished: show a draft label and the explicit publish action.
- Long Chinese, English, mixed, and version text: card labels stay single-line with truncation and a full accessible title.
- Reduced motion: no moving/looping persona animation. Reduced transparency uses existing solid-surface fallback.

## Accessibility and Responsive Requirements

- Persona images receive meaningful generated alt text. Decorative portions are hidden from assistive technology.
- Candidate cards are keyboard reachable; selection has an accessible pressed/selected state.
- Every image-inspection, switcher, and icon-only action has a text label or accessible name.
- At 1280px, gallery, brief, and hero preserve their three-region hierarchy. At 1024px, the hero moves into a single collapsible region; no document-wide horizontal overflow is permitted.
- Chinese action labels remain at four characters or fewer. English labels remain short, use `white-space: nowrap`, and move to icon-plus-tooltip controls when toolbar budget is exhausted.
